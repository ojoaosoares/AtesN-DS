\begin{abstract}
DNS is fundamental to the Internet, but traditional user-space resolvers incur high overhead from network stack traversal. Kernel-space designs such as AtesN-DS reduce this cost by executing resolution in the eBPF/XDP driver layer, yet performance still degrades under heavy concurrency because of host interrupts and PCIe traffic. This paper presents a hybrid extension that combines driver-space execution with programmable SmartNIC offloading. A new cache layer is created in the NIC, where cache hits are resolved at line rate without crossing the PCIe bus or triggering host interrupts; misses fall back to the AtesN-DS driver-space resolver. To validate the architecture under genuine Internet conditions, comprehensive empirical evaluations were conducted on a physical testbed by replaying a real-world enterprise DNS traffic trace captured in an active university campus network. Results demonstrate that augmenting AtesN-DS with the hardware-offloaded cache layer sustains a consistent 1.64$\times$ to 1.70$\times$ throughput speedup across the operational saturation plateau (reaching a peak speedup of up to 1.80$\times$ at 4 connections, with a maximum capacity of over 172,000\,Queries/s, equivalent to 10.35\,M queries/min) and reduces mean latency by up to 38.1\% for workloads spanning up to 4,096 simultaneous connections compared to its standalone driver-space execution. Under this real trace workload, the SmartNIC hardware cache achieves a stable hit rate of up to 72.8\%, filtering over 7.5 million queries in complete host bypass and pushing the system's throughput-latency saturation knee beyond 166,000\,Queries/s. Furthermore, the offloaded architecture sustains a 1.52$\times$ throughput advantage under peak stress of 16,384 connections, delivers a +120\% to +141.6\% increase in computational efficiency (sustaining over 91,000\,Queries/s per 1\% host CPU), reduces host SoftIRQ overhead by up to 36.5\%, and keeps global host CPU utilization strictly below 2.15\% across all tested scenarios.\end{abstract}

\section{Introduction}

The Domain Name System (DNS) is a distributed and hierarchical protocol originally specified by Mockapetris~(\cite{rfc1035, mockapetris1987domain}) that translates human-understandable domain names into machine-readable IP addresses. Currently, DNS is an indispensable part of the Internet; beyond being the pivot for name resolution, it also enables users to locate services~(\cite{cheshire2013dns}) and load balancing~(\cite{brisco1995dns}). Furthermore, CDNs utilize DNS to route clients to the geographically closest servers based on their location~(\cite{hours2016study}) and to identify malicious botnets~(\cite{choi2007botnet}). Thus, the global impact of DNS becomes evident, highlighting the importance of studies aimed at reducing name resolution time and the efficiency of this process.

The DNS infrastructure relies on recursive resolvers to close the gap between clients and authoritative servers. When a requested domain is missing from the local cache, the resolver must initiate an iterative traversal across the DNS hierarchy, a process that can trigger hundreds of nested messages for a single resolution in worst-case scenarios~(\cite{afek2020nxnsattack}). Because traditional architectures implement these resolvers in user space~(\cite{6932501}), every incoming and outgoing packet from this multi-hop sequence is forced to traverse the entire operating system network stack. This traversal triggers heavy performance penalties through continuous context switches and memory copies, consuming up to half of the available host CPU cycles even during baseline operations~(\cite{10.1145/3672197.3673439}), which directly translates into tail-latency inflation for end-user applications~(\cite{singla2014internet}).

To mitigate these bottlenecks, high-performance packet processing frameworks have increasingly explored kernel-bypass and programmable data-plane paradigms. Prominent user-space bypass frameworks, such as the Data Plane Development Kit (DPDK)~(\cite{kourtis2015enhancing}) and AF\_XDP sockets~(\cite{10.1145/3281411.3281443}), accelerate packet ingestion by delivering frames directly to user space. However, these host-side frameworks present fundamental trade-offs: DPDK relies on aggressive Poll Mode Drivers (PMD) that monopolize 100\% of dedicated CPU cores in busy-waiting loops even when traffic is low, while completely severing integration with the Linux network stack and requiring basic networking protocols, routing, and firewalling to be laboriously re-implemented within application code. Furthermore, because both DPDK and AF\_XDP execute strictly on the host CPU, neither framework can synthesize an answer before the packet physically crosses the PCIe bus and consumes host memory bandwidth. In contrast, the extended Berkeley Packet Filter (eBPF) and the Express Data Path (XDP)~(\cite{10.1145/3281411.3281443}) provide an event-driven, kernel-cooperative execution model that preserves standard OS networking primitives while enabling packet handling directly at the driver layer without dedicated-core polling overhead~(\cite{vieira2020fast, 9665095}). Crucially, XDP uniquely extends this paradigm to a hardware offload mode, enabling bytecode to execute directly inside the silicon of programmable SmartNICs.

Consequently, recent studies have shown that DNS resolvers placed directly in the XDP hook can achieve very high performance and substantially lower latency~(\cite{sbesc_estendido, 10.1145/3672197.3673439}). However, leveraging XDP hardware offload for stateful DNS resolution introduces distinct architectural challenges. Because of strict SmartNIC silicon limits on instructions and memory, realizing an entire iterative resolver directly in the hardware data plane is impractical.

To overcome these constraints, this study proposes a hybrid architecture that extends the AtesN-DS framework~(\cite{sbesc_estendido}) by combining its XDP driver-based resolver with a multi-tier cache structure built around XDP hardware offloading. By orchestrating a high-performance DNS cache directly on the programmable hardware alongside a secondary, larger cache layer in the driver space, the system can intercept and resolve the majority of queries at line rate. Under this design, the offloaded hardware cache and the AtesN-DS native resolver immediately process queries within the accelerated data plane, while the user-space resolver is utilized only as a fallback mechanism to handle specific unhandled query types or severe traffic overloads.

In summary, the primary contributions of this work are threefold: $(i)$ the design and implementation of a hybrid, multi-tier DNS resolver architecture that harmonizes XDP hardware offloading with kernel driver-space execution; $(ii)$ an open-source framework demonstrating the practical feasibility of executing bounded, state-synchronized DNS caching tables within strict SmartNIC hardware limitations; and $(iii)$ a comprehensive experimental evaluation comparing driver-mode and hardware-offloaded configurations driven by a real-world enterprise DNS traffic trace collected in an active university network. Rather than relying on synthetic uniform benchmarks, our evaluation replays genuine campus DNS queries to expose realistic domain popularity skewness, temporal locality, and trade-offs in latency, throughput, cache filtering, and host CPU decoupling under intense concurrency. 

Compared with the standalone driver-mode AtesN-DS resolver, the offloaded architecture sustains a consistent throughput speedup of 1.64$\times$ to 1.70$\times$ across the operational saturation plateau (peaking at up to 1.80$\times$ at 4 connections and reaching an overall capacity of 172,468\,Queries/s, or 10.35\,M queries/min), reduces average latency by up to 38.1\% for workloads spanning up to 4,096 simultaneous connections, and maintains a robust 1.52$\times$ throughput advantage under peak stress of 16,384 connections. The SmartNIC hardware cache sustains a hit rate of up to 72.8\%, resolving nearly three-quarters of all requests in silicon and shifting the throughput-latency saturation knee from 101.8k to over 166k\,Queries/s. Furthermore, by shifting processing to the SmartNIC, the system boosts computational efficiency by +120\% to +141.6\% (delivering over 91,000\,Queries/s per 1\% host CPU), reduces host SoftIRQ overhead by up to 36.5\%, lowers overall host CPU consumption by up to 33.6\% (keeping it strictly under 2.15\% across all tested scenarios), and caps peak utilization of the most strained network core below 7.85\%.

Section~\ref{sec:evaluation} presents the experimental setup and analyzes the performance evaluation results, highlighting the trade-offs in throughput, latency, and resource utilization. Finally, Section~\ref{sec:conclusion} concludes the paper and discusses directions for future work.

\section{Literature Review}
\label{sec:related_work}

This section reviews core advancements in high-performance network services, kernel-embedded data planes, and in-network acceleration. We first describe the baseline AtesN-DS driver-mode recursive resolver in detail, establishing its operational mechanics and limitations. We then position our hybrid architecture against prior in-NIC and in-network acceleration systems, including FPGA-based responders, switch data-plane caches, in-kernel key-value caches, and pre-stack datagram offloaders. Finally, we contrast our contribution against the original conference paper (SBESC 2025) to delineate the new architectural extensions introduced in this journal version.

\subsection{The Baseline Driver-Mode AtesN-DS Recursive Resolver}
\label{sec:driver_mode_resolver}

The foundation of our work is the AtesN-DS recursive DNS resolver framework~(\cite{sbesc_estendido}). Operating directly at the native driver-level eBPF/XDP hook (\texttt{XDP\_DRV}), AtesN-DS is designed to eliminate the severe operating system overheads inherent to traditional user-space resolvers. In conventional architectures, every incoming DNS query and outgoing authoritative resolution sequence must traverse the entire Linux network stack, incurring memory allocation penalties (\texttt{sk\_buff} allocation), SoftIRQ interrupt scheduling delays, and user-kernel context switching. Under high traffic volumes, these traversals consume substantial CPU cycles and induce tail-latency inflation.

To circumvent these bottlenecks, AtesN-DS embeds the resolution data path directly into the network device driver. The driver-mode resolver operates as follows:
\begin{enumerate}
    \item \textbf{Ingress Interception and Packet Parsing:} Upon packet arrival, the driver-space eBPF program intercepts UDP datagrams destined for port 53 directly from the network ring buffer. It validates Ethernet, IPv4, and UDP headers using direct memory pointers, verifying that the payload represents a well-formed DNS message. It parses the DNS header flags and extracts the Question section (query name, $\text{QTYPE}$, and $\text{QCLASS}$).
    \item \textbf{In-Driver Cache Hierarchy (\texttt{sw\_cache}):} The resolver queries an in-kernel BPF hash map (\texttt{sw\_cache}, preallocated with a capacity of up to 4,000,000 entries). Unlike hardware-constrained tables, \texttt{sw\_cache} resides in host main memory and supports full RFC~1035 domain names (up to 253 characters) and multiple resource records. Each entry stores the resolved IPv4/IPv6 addresses, record TTL, and an absolute expiration epoch timestamp. If a matching record is found and its TTL is valid, AtesN-DS immediately crafts a DNS response in-place, updates transport checksums, swaps source and destination MAC/IP addresses, and retransmits the frame directly back to the client interface using \texttt{XDP\_TX}, bypassing the upper host networking stack entirely.
    \item \textbf{Recursive Multi-Hop State Tracking (\texttt{queries\_map}):} On a cache miss, AtesN-DS must resolve the domain recursively without delegating to user space. To track in-flight asynchronous resolutions across multi-hop iterations (contacting root, TLD, and authoritative servers), the driver resolver allocates an in-flight transaction context within the \texttt{queries\_map} (sized for up to 4,587,576 concurrent queries). This table correlates the client's original transaction ID, IP address, and UDP port with a newly generated upstream transaction ID.
    \item \textbf{Upstream Zone Mapping (\texttt{ns\_cache}):} To minimize iterative traversal delays, AtesN-DS maintains an authoritative nameserver cache (\texttt{ns\_cache}, holding up to 8,000,000 zone records). This table maps domain zones and TLDs to known upstream nameserver IP addresses. If the target zone's nameserver is cached, AtesN-DS constructs an upstream iterative query and transmits it via \texttt{XDP\_TX} (or forwards it to the upstream WAN gateway). When the authoritative server returns a response, AtesN-DS intercepts the incoming packet, matches its transaction ID in \texttt{queries\_map}, updates \texttt{sw\_cache} with the newly learned A record, reconstitutes the client-facing response packet, and transmits it directly to the requesting host.
    \item \textbf{Proactive Cache Renewal (Prefetching):} To prevent latency spikes when popular domain records expire, AtesN-DS incorporates a proactive renewal mechanism. A lightweight user-space daemon monitors query access frequencies; when a frequently requested domain approaches its TTL expiration threshold, the daemon initiates a prefetch resolution to refresh the in-kernel cache before client requests experience a cold miss.
    \item \textbf{Selective Kernel and User-Space Fallback:} While AtesN-DS natively handles standard $\text{A}$/$\text{IN}$ iterative queries at line rate, handling complex or edge-case DNS protocol features (such as non-A query types, TCP connection fallbacks, DNSSEC signature validation, or EDNS0 large buffer negotiations) in eBPF would exceed kernel verifier instruction limits. Consequently, any packet exhibiting unhandled query types, malformed headers, or table saturation safely yields an \texttt{XDP\_PASS} action, allowing the frame to cascade cleanly into the standard host network stack and fall back to a full-featured user-space resolver (such as Unbound).
\end{enumerate}

While AtesN-DS in driver mode delivers substantial throughput gains over user-space solutions, its performance under massive concurrency is fundamentally bounded by host hardware interrupts: every incoming packet still crosses the physical PCIe bus into host RAM, triggering NIC Receive Ring Buffer DMA transfers, PCIe MSI-X interrupts, and host SoftIRQ processing. Under saturation (e.g., beyond 4,096 concurrent connections), host core saturation and PCIe queueing introduce throughput plateaus and tail-latency jitter. This limitation motivates our hybrid hardware-offloaded architecture.

\subsection{Positioning the Hardware Caching Layer Against Prior In-NIC and In-Network Systems}
\label{sec:positioning_prior_work}

To contextualize our hardware acceleration layer (\texttt{hw\_cache}), we directly contrast its in-silicon data-plane design
against prominent prior hardware and pre-stack accelerators across programmable FPGAs, switch ASICs, and in-kernel caches. We
emphasize that, consistent with prior in-network and in-NIC accelerators (such as Emu DNS, P4DNS, and NetCache), the SmartNIC
hardware data plane of AtesN-DS operates strictly as a line-rate caching and answer-generation engine rather than an in-silicon
recursive resolver. Maintaining recursive resolution state in hardware silicon is fundamentally intractable: iterative traversal
requires tracking complex multi-hop dependency graphs, maintaining transaction contexts across hundreds of asynchronous sub-queries,
reassembling out-of-order responses, and managing recursive timeout trees. Storing this state demands at least 256 bytes per active
connection, far exceeding the SmartNIC firmware's 64-byte map entry ceiling, and requires thousands of stateful instructions that
would shatter the NFP-4000's 1,536-instruction budget. By deliberately decoupling line-rate caching (handled entirely in SmartNIC
silicon) from recursive resolution (delegated to the host driver and user space), AtesN-DS achieves the best of both worlds: line-
rate host bypass for high-frequency hits, with zero-network-hop fallback to full recursive capabilities on the host. Below, we
compare our hardware caching tier against related data-plane systems:

\textbf{Emu DNS on NetFPGA:} Sultana et~al.~(\cite{203245}) introduced \textit{Emu}, a framework for rapid prototyping of
networking services on NetFPGA SUME boards using a C\#-to-FPGA high-level synthesis (HLS) compiler, implementing an authoritative DNS
responder in FPGA silicon. While Emu demonstrates ultra-low packet latency, its standalone hardware design highlights key eviction
and fallback trade-offs. In terms of cache eviction, Emu stores records in FPGA Block RAM (BRAM) without dynamic replacement;
synthesizing fine-grained LRU or TTL-tracking state machines directly in FPGA logic is notoriously complex, consuming scarce logic
slices (LUTs/DSPs) that would otherwise serve packet processing pipelines, thereby forcing reliance on static table allocations.
Furthermore, implementing an automated fallback to host resolution software on an FPGA is technically cumbersome, requiring a custom
PCIe DMA bridge and dedicated kernel drivers to be synthesized from scratch. In contrast, AtesN-DS avoids custom hardware synthesis
by using standardized eBPF/XDP on a commodity SmartNIC (Netronome Agilio CX). Here, the tight SmartNIC-host co-design makes eviction
policies vastly simpler and more effective: rather than burning silicon logic on eviction hardware, AtesN-DS delegates eviction
governance to a host DRAM circular timing wheel that selects victim slots in $\mathcal{O}(1)$ without PCIe reads via \textit{Passive
Evict-on-Write}. Moreover, fallback is inherently native: any hardware miss returns \texttt{XDP\_PASS}, immediately handing the frame
to the co-located host driver over standard DMA ring buffers with zero network hops.

\textbf{P4DNS and In-Switch DNS Processing:} Several works have explored offloading DNS parsing and resolution into programmable
network switches using P4~(\cite{10619855}). For instance, Woodruff, Ramanujam, and Zilberman developed P4DNS, which maps DNS query
matching and response generation into switch Match-Action Tables (MAT), while Kumar et~al.~(\cite{10619855}) investigated 
application-layer header parsing in P4. While in-switch resolution sustains massive aggregate line-rate throughput, switch pipelines
face rigid eviction and fallback constraints. Because switch ASICs are strictly feed-forward, they cannot maintain dynamic linked
lists or sweep memory for TTL expiration in the data plane; eviction requires an external switch CPU to periodically poll match
counters and issue table-delete RPCs, creating high latency and control-plane bottlenecks under DNS churn. Additionally, because
switches reside inside the network fabric physically separated from application servers, fallback on a cache miss cannot occur
locally over PCIe, forcing packets across extra physical network hops to remote backend servers. AtesN-DS overcomes both hurdles via
endhost SmartNIC-host co-design: misses cascade directly to the local host driver with zero network latency, while eviction is
governed asynchronously by the host daemon across 2,000,000 entries in SmartNIC DRAM, enabling sophisticated dual-watermark and
minimum-TTL policies without switch hardware limitations or data-plane stalls.

\textbf{NetCache:} Jin et~al.~(\cite{10.1145/3132747.3132764}) developed \textit{NetCache}, an in-network key-value cache on
Barefoot Tofino switch ASICs that absorbs load skews in distributed storage systems (e.g., Memcached) at over two billion queries per
second. However, NetCache's hardware caching pipeline reveals fundamental differences in eviction and application scope compared to
AtesN-DS. NetCache detects heavy hitters via data-plane sketches, but cannot evict items autonomously: cache replacement requires an
external controller to aggregate statistics, compute victims, and push table updates down to the switch, introducing high reaction
latency that is ill-suited for DNS where millions of entries expire with dynamic, second-resolution TTLs. Furthermore, NetCache is
restricted to fixed 16-byte keys and 128-byte values capped at 64,000 entries in switch SRAM, unable to parse variable-length, multi-
label DNS QNAMEs, and misses must be routed over the network to storage nodes. In contrast, AtesN-DS leverages the server's SmartNIC
adapter to store 2,000,000 entries in onboard DRAM with up to 56-byte domain keys. By synchronizing epoch time once per second via
\texttt{time\_map}, the SmartNIC autonomously validates TTLs in silicon in $\mathcal{O}(1)$, while table eviction is executed locally
and on-demand by the host daemon upon insertion, eliminating off-path controller overhead entirely.

\textbf{BMC (Safe In-Kernel Caching):} Ghigoff et~al.~(\cite{performance:bmc}) presented \textit{BMC}, an in-kernel cache for
Memcached that uses eBPF at the driver-space XDP hook (\texttt{XDP\_DRV}) to serve UDP \texttt{GET} queries directly from kernel BPF
maps, avoiding context switches and socket buffers. However, analyzing BMC illustrates why in-kernel software caching cannot match a
hardware offload tier. Crucially, BMC relies on the Linux kernel's \texttt{BPF\_MAP\_TYPE\_LRU\_HASH} for automatic eviction; when
porting eBPF to physical SmartNIC silicon (\texttt{XDP\_HW}), the hardware verifier and firmware strictly reject LRU maps due to the
lack of hardware lock and linked-list primitives in silicon, preventing BMC's caching design from offloading to hardware as-is.
Furthermore, because BMC executes strictly on host CPU cores, 100\% of incoming packets must cross the physical PCIe bus and generate
host SoftIRQs (\texttt{NET\_RX}), consuming host CPU cycles under heavy load. AtesN-DS bridges this gap: by introducing
\textit{Passive Evict-on-Write}, AtesN-DS enables standard hash maps (\texttt{BPF\_MAP\_TYPE\_HASH}) to function as self-governing
caches in SmartNIC silicon without native LRU support, resolving up to 72.8\% of queries directly in hardware before packets ever
cross PCIe or interrupt the host CPU.

\textbf{Application-Agnostic Datagram Offloading (Santa):} Hohlfeld et~al.~(\cite{8493053}) proposed \textit{Santa}, a pre-stack
kernel rule processor that accelerates UDP datagrams in the Linux kernel by matching packets against predefined rule tables,
demonstrating a 5.5$\times$ speedup for DNS over user-space BIND. However, like BMC, Santa is an in-kernel software module running
exclusively on general-purpose host CPUs, unable to eliminate PCIe transfer overhead or host interrupt generation. Moreover, its rule
engine lacks dynamic data-plane eviction: rules are statically managed by user space without data-plane TTL validation or automatic
working-set replacement, and porting such a rule table to a NIC would quickly hit hardware saturation without active eviction
governance. AtesN-DS significantly advances beyond static software rule matching by moving the caching tier into physical SmartNIC
silicon and integrating an autonomous, time-synchronized eviction pipeline: by coupling an in-host DRAM circular timing wheel with
atomic on-demand insertion over PCIe, AtesN-DS maintains line-rate throughput and zero packet loss even under heavy working-set
saturation.



\subsection{Novelty and Extensions Relative to the SBESC 2025 Paper}
\label{sec:novelty_sbesc}

The preliminary version of AtesN-DS presented at SBESC 2025~(\cite{sbesc_estendido}) introduced the concept of an in-kernel recursive DNS resolver executing entirely in software at the native XDP driver layer (\texttt{XDP\_DRV}). While the conference paper established the viability of kernel-space recursive resolution, it operated exclusively on the host CPU, meaning that all traffic traversed the physical PCIe bus and generated host SoftIRQs. 

This journal article significantly expands upon the SBESC 2025 conference paper through five major architectural, algorithmic, and empirical contributions:
\begin{enumerate}
    \item \textbf{Hardware Data-Plane Offloading (\texttt{XDP\_HW}):} We design and implement the first hybrid DNS architecture that offloads stateful caching directly into the silicon of a programmable SmartNIC (Netronome Agilio CX 2$\times$10GbE), enabling line-rate cache hits to be answered in hardware with zero PCIe transfers, zero host DMA, and zero host CPU interrupts.
    \item \textbf{Optimized 56-Byte Key and 64-Byte Aligned Cache Architecture:} To overcome the strict physical memory and instruction limits of network microengines, we restructured the offloaded packet inspection pipeline into an optimized, two-phase bounded unrolling scheme. This reduced the compiled eBPF bytecode to \textbf{589 native instructions} (utilizing just 38.3\% of the 1,536-instruction budget) and enabled an optimal 64-byte entry layout (56-byte domain key + 8-byte value) that accommodates 2,000,000 records in 128\,MB of SmartNIC DRAM with natural memory alignment.
    \item \textbf{Zero-PCIe-Read Passive Eviction and Host Timing Wheel:} Because SmartNIC silicon lacks native LRU map support (\texttt{BPF\_MAP\_TYPE\_LRU\_HASH}), naively polling hardware tables over PCIe to evict expired records triggers severe interconnect saturation and hash bucket locking. We introduce the \textit{Passive Evict-on-Write Daemon} and a host-side 86,400-bucket circular timing wheel that tracks domain expirations with zero PCIe read traffic, executing $\mathcal{O}(1)$ on-demand replacements with negligible host CPU overhead ($0.053\%$).
    \item \textbf{Asymmetric, Tamper-Proof Cache Population (DNS Listener):} To prevent unauthenticated or spoofed packets on the wire from directly altering hardware state, we introduce the decoupled \textit{DNS Listener}. Operating as a verified eBPF filter at the host driver hook, it statefully matches authoritative responses against in-flight queries before feeding valid A records into an asynchronous host ring buffer, which a privileged daemon commits over PCIe DMA. This design ensures complete cache-poisoning protection and allows the hardware cache to be deployed transparently in front of standard upstream resolvers (e.g., BIND or Unbound) without source code modification.
    \item \textbf{Comprehensive Real-World Campus Trace Evaluation and Tail-Latency Analysis:} While the conference paper evaluated synthetic uniform traffic, this work conducts exhaustive empirical evaluations on a physical point-to-point testbed replaying a genuine enterprise DNS trace from an active university campus. We expand the evaluation scope to report tail latency ($p_{50}$, $p_{90}$, $p_{99}$, $p_{99.9}$), packet loss, host SoftIRQ reduction, single-core CPU saturation, and SmartNIC hardware resource utilization across workloads up to 16,384 concurrent connections.
\end{enumerate}

\subsection{Latency, Caching, and eBPF in Modern Systems}
\label{sec:background_latency_caching}

Several studies have investigated the critical impact of network latency on user experience~(\cite{attig2017system}), including extensive research on web browsing~(\cite{arapakis2021impact}) and cloud-based applications~(\cite{claypool2014effects}). Among these works, some identify the operating system network stack as one of the primary bottlenecks responsible for latency inflation~(\cite{singla2014internet}). To overcome this architectural limitation, researchers have developed highly efficient network stacks~(\cite{10.1145/2740070.2626311}) as well as stack-bypass strategies~(\cite{10.1145/3297156.3297242}). Notable paradigms among these bypass techniques include the Data Plane Development Kit (DPDK)~(\cite{kourtis2015enhancing}) and the adoption of eBPF/XDP~(\cite{cai2021understanding}).

Beyond bypassing network stack traversals, caching represents another well-established strategy for latency reduction, with eBPF emerging as a highly effective enabler for in-kernel cache implementations. Frameworks such as \texttt{cache\_ext}~(\cite{zussman2025cache_ext}) and LearnedCache~(\cite{qi2026learnedcache}) (which leverages perceptron-based eviction policies) demonstrate the effectiveness and versatility of eBPF in customizing OS page cache management, while MiddleCache~(\cite{pang2023middlecache}) extends in-kernel caching to support TCP-based queries.

Beyond packet filtering, recent works have leveraged eBPF to bypass upper-layer kernel overheads in both storage and transport subsystems. For instance, XRP~(\cite{280870}) enables user-defined storage functions, such as index lookups and aggregations to execute directly within an eBPF hook in the NVMe driver, drastically reducing OS storage stack overheads for microsecond-scale devices. Similarly, eTran~(\cite{chen2025etran}) extends eBPF to make the kernel networking stack agilely extensible, allowing developers to safely implement and customize complex transport designs, such as TCP congestion controls and clean-slate protocols like Homa, directly within the Linux kernel while achieving near user-space performance. As eBPF adoption expands across diverse system domains, ensuring execution isolation and multi-tenant security becomes critical, addressed by vBPF~(\cite{zhang2026virtualizing}) via late-binding virtualization and KrakenGuard~(\cite{patel2026krakenguard}) via symbolic execution at load time. Furthermore, Abranches~et~al.~(\cite{9665095}) demonstrate that leveraging eBPF with XDP for network monitoring yields higher computational efficiency compared to kernel-bypass alternatives like DPDK. Moving beyond general-purpose host CPUs, platforms such as hXDP~(\cite{performance:hxdp}) and eBPFlow~(\cite{performance:ebpflow,networking:application_layer}) demonstrate that offloading packet processing to FPGAs programmed with eBPF can achieve ultra-low latency and high throughput.

\section{Proposed System}
\label{sec:proposed_system}

This section describes the proposed multi-tier DNS design and implementation, which routes packet processing across hardware, the driver, and user space. To maximize throughput, the core resolver extends the AtesN-DS framework~(\cite{sbesc_estendido}) and runs as an in-kernel recursive resolver at the XDP hook. The main novelty, however, is offloading the DNS cache to specialized hardware in XDP offload mode.

\subsection{Design}

To maximize packet processing throughput while working around the resource constraints of network hardware, our system adopts a hybrid, multi-tier resolution architecture (depicted in Figure~\ref{fig:1}). Instead of processing all DNS logic within a single execution tier, the system decouples high-frequency caching from full recursive resolution across three specialized operational levels: an offloaded hardware data plane in the SmartNIC silicon, an in-kernel driver resolver, and a user-space control and fallback tier. 

The core of the hardware offload layer operates as a line-rate, read-mostly cache executing directly within the NIC silicon, dedicated to accelerating client query resolution while decoupling cache population to authenticated host control channels. For incoming client DNS queries, the hardware cache inspects the requested domain name. On a cache hit with a valid TTL, the NIC directly constructs the DNS answer, rewrites transport headers, and retransmits the frame back to the client at line rate (\texttt{XDP\_TX}), completely bypassing host interrupts, PCIe bus traversals, and upper-stack overhead. Conversely, on a cache miss or TTL expiration, the query cleanly cascades down over PCIe via \texttt{XDP\_PASS} to the native AtesN-DS driver layer for high-throughput recursive resolution or to user space under severe traffic overloads. Crucially, the hardware data plane enforces strict immutability against wire packets: it contains no write or insertion logic for external responses. Incoming DNS responses arriving from the network wire immediately yield \texttt{XDP\_PASS} to the host stack, ensuring that raw network frames cannot directly alter hardware memory. As detailed below, cache population is handled exclusively through an asymmetric control-plane pipeline fed by verified host resolutions.

To maintain hardware simplicity and keep the offloaded data plane lightweight, the architecture delegates state maintenance and cache lifecycle functions to dedicated user-space control daemons running on the host. First, a \textit{time daemon} periodically synchronizes the host epoch clock with the hardware memory, enabling the offloaded data plane to perform absolute TTL freshness validation during packet processing without requiring native hardware timer support. Second, to manage cache saturation and stale record reclamation in the absence of native hardware LRU support, we developed the \textit{Passive Evict-on-Write Daemon}, which couples an in-host DRAM timing wheel with reactive on-demand eviction directly tied to record insertion. As detailed in Section~\ref{sec:implementation} and empirically demonstrated in Section~\ref{sec:saturation_eval}, this passive architecture sustains 100\% hardware cache capacity without artificial headroom buffers, operates with negligible host CPU overhead, and completely eliminates PCIe interconnect storms and hash bucket spinlock contention on the SmartNIC datapath.

As shown in Figure~\ref{fig:1}, dark blue highlights the components of the hardware-offloaded cache subsystem, encompassing both the in-NIC data plane and the host-side control daemons, and gray represents the native driver-space AtesN-DS resolver stack.

The proposed hardware cache architecture cleanly decouples high-speed query answering from recursive resolution. To enable modular and secure cache population, we introduce the \textit{DNS Listener}, a lightweight eBPF program attached to the native (driver) or generic (emulated) XDP hook. The DNS Listener operates in two deployment modes: (1)~\textit{Integrated Mode}, embedded directly within the in-kernel AtesN-DS resolver, or (2)~\textit{Standalone Mode}, functioning as an autonomous network filter positioned transparently in front of any standard upstream resolver (such as BIND, Unbound, or PowerDNS). By intercepting outgoing queries and incoming authoritative responses at the XDP layer, the DNS Listener statefully tracks in-flight DNS transactions (recording transaction IDs, randomized UDP ports, and domain names). Only when an incoming response strictly matches an outstanding in-flight query does the DNS Listener extract the validated A record and dispatch an event to the host ring buffer (\texttt{hw\_sync\_ringbuf}). A privileged host user-space daemon subsequently commits the record to the SmartNIC lookup table via \texttt{bpf\_map\_update\_elem} over PCIe DMA. This design delivers strong architectural security and complete modularity: unauthenticated or spoofed packets from the network wire cannot bypass resolution validation or pollute the in-silicon lookup table, and the hardware caching layer can be seamlessly coupled with any existing DNS server software without modifying its internal source code.

Because these operational tiers execute in complete isolation without sharing state or parsed packet metadata, each layer must independently parse the DNS query header upon packet arrival. In the event of a cache miss at lower hardware layers, this decoupled inspection introduces a negligible parsing overhead, as upper host layers must re-parse the domain upon receiving the forwarded packet. However, this trade-off yields substantial performance dividends: on a cache hit, the hardware data plane resolves the query entirely in silicon, completely bypassing host interrupts, PCIe bus traversal, and upper-stack overhead. Ultimately, this isolated design was chosen for architectural simplicity, ensuring modularity, robust fallback mechanisms, and zero modification requirements for existing upstream resolution software.

\subsection{Implementation}
\label{sec:implementation}

The hardware-level caching layer was implemented using the eBPF/XDP offload framework, attaching the data plane execution directly to the SmartNIC silicon. While eBPF/XDP offloading has emerged as a compelling paradigm for line-rate packet processing, adapting high-level stateful application logic such as a DNS lookup table to network interface hardware introduces two fundamental architectural challenges: time abstraction and restricted map operations. The overall architecture and execution pipeline of this hardware-level caching mechanism are illustrated in Figure~\ref{fig:hw_pipeline}.

First, because the XDP offload engine lacks time-based helpers such as \texttt{bpf\_ktime\_get\_ns()}, the hardware data plane has no intrinsic notion of time to evaluate domain TTL expiration. To bridge the host clock to the SmartNIC, the architecture employs a single-element \texttt{BPF\_MAP\_TYPE\_ARRAY} named \texttt{time\_map} (depicted in Figure~\ref{fig:hw_pipeline}). Standard eBPF array maps mandate a 32-bit unsigned integeras the key index. The map value is also a 4-byte unsigned integer holding the global epoch timestamp in seconds. A lightweight host-side \textit{time daemon} (Figure~\ref{fig:1}) periodically writes the current host epoch timestamp to index zero once per second ($1\,\text{Hz}$), providing fine-grained 1-second TTL accuracy with negligible host overhead. During packet lookup, the offloaded program performs an $\mathcal{O}(1)$ query against index zero, enabling in-NIC TTL validation by comparing the retrieved epoch against stored record expiration timestamps.


%%% OLHAR ESSE PARAGRAFO
Second, SmartNIC hardware architectures inherently lack silicon support for native Least Recently Used (LRU) maps (\texttt{BPF\_MAP\_TYPE\_LRU\_HASH}), which would otherwise manage record eviction automatically upon table saturation. This hardware limitation forces the caching mechanism to rely on a standard hash map (\texttt{BPF\_MAP\_TYPE\_HASH}), instantiated within the offloaded program as \texttt{hw\_cache} (depicted in Figure~\ref{fig:hw_pipeline}). In the Netronome NFP architecture, large eBPF maps are allocated in the SmartNIC's onboard DRAM (external memory) rather than limited on-chip memory, subject to firmware allocation bounds. To balance memory density with comprehensive domain name coverage across the SmartNIC's onboard memory, the map entry is structured with a 56-byte key, accommodating fully qualified domain names up to 56 characters, and an 8-byte value containing two 32-bit unsigned integers: a 4-byte IPv4 response address and a 4-byte absolute expiration timestamp. Crucially, this 56-byte key combined with the 8-byte value yields a total entry size of exactly 64 bytes, perfectly matching the hardware's 64-byte memory alignment boundary and optimizing DRAM access patterns.

While empirical findings by Ma et al.~\cite{ma2022dnstunnelslidingwindow} indicate that real-world DNS query names follow a distribution with a mean length of approximately 13 characters, domain names exceeding 56 characters are statistically exceptional. Consequently, this 56-byte key layout achieves an optimal trade-off, seamlessly accommodating practically all real-world DNS traffic while maximizing total record capacity and ensuring natural 64-byte memory alignment within the SmartNIC's firmware-supported allocation limits.

Because standard \texttt{BPF\_MAP\_TYPE\_HASH} tables cannot autonomously purge stale entries when capacity is reached, managing the lifecycle of cached records relies on a coordinated dual-plane operational strategy. At the hardware data plane, the offloaded XDP program performs inline lazy TTL evaluation, checking entry freshness during packet lookup and triggering immediate $\mathcal{O}(1)$ deletions via \texttt{bpf\_map\_delete\_elem} upon encountering expired records. However, because low-frequency or cold stale records may not be accessed again by client queries, relying solely on data-plane lookups would eventually lead to capacity exhaustion. 

To address hardware capacity limits and ensure that no newly resolved domain records are lost upon reaching table saturation, the system integrates the Passive Evict-on-Write Daemon. Instead of performing costly periodic sweeps across the PCIe bus, the host control plane maintains an in-DRAM \textit{Timing Wheel}, a hierarchical, slotted circular array that tracks record expiration lifetimes with zero PCIe interaction.

In this passive paradigm, background sweeps across the network card are completely eliminated. Eviction is triggered strictly on demand upon inserting a newly resolved DNS record. During an unsaturated state, when the hardware table has not reached capacity, the ingestion worker immediately issues an $\mathcal{O}(1)$ \texttt{bpf\_map\_update\_elem} over PCIe DMA and registers the key alongside its expiration epoch in the host DRAM timing wheel. Conversely, during a saturated state, when the hardware table is full, the ingestion worker executes a deterministic $\mathcal{O}(1)$ 1-for-1 demand replacement: it retrieves a victim from the Timing Wheel, which prioritizes popping already expired records or, if none are yet expired, the record with the minimum remaining TTL. The worker then issues an individual \texttt{bpf\_map\_delete\_elem} to evict the victim from the SmartNIC, immediately followed by \texttt{bpf\_map\_update\_elem} to admit the new entry.

From an execution perspective, the packet processing pipeline branches based on DNS message headers and protocol semantics evaluated inline at the SmartNIC ingress (depicted in Figure~\ref{fig:hw_pipeline}). Upon packet arrival, the offloaded XDP program verifies that the frame represents an IPv4 UDP packet directed to port 53. To enforce strict type isolation and prevent cache pollution across different resource classes, the parser explicitly validates that the query contains a single question with $\text{QTYPE}=\text{A}$ and $\text{QCLASS}=\text{IN}$. Any query requesting alternative record types (such as \texttt{AAAA}, \texttt{MX}, \texttt{TXT}, \texttt{SRV}, or \texttt{CNAME}), non-IN classes, or advertising large EDNS0 buffers immediately returns \texttt{XDP\_PASS}, cascading untouched to the host resolver stack. Also, queries requiring full multi-IP RRsets or DNSSEC cryptographic validation ($\text{DO}=1$) are handled in host software. By verifying $\text{A}/\text{IN}$ as a mandatory precondition in bytecode, the hardware lookup table can dedicate its 56-byte key budget exclusively to the domain name, avoiding wasting key bytes on static type and class identifiers within the SmartNIC's hardware memory layout.

For eligible A-record queries, the program retrieves the current epoch from \texttt{time\_map} and executes an $\mathcal{O}(1)$ lookup against \texttt{hw\_cache} using the extracted \texttt{QNAME}. On a cache hit, the hardware validates freshness by dynamically calculating the decaying remaining TTL. If the remaining is less than $1\,\text{s}$, the record is deemed expired, triggering inline eviction via \texttt{bpf\_map\_delete\_elem} and forwarding the query to the host via \texttt{XDP\_PASS}. Otherwise, the hardware engine synthesizes the DNS answer entirely in silicon: it preserves the client's 16-bit Transaction ID in place, sets response flags to $\text{QR}=1$, $\text{RD}=1$, $\text{RA}=1$, $\text{RCODE}=\text{NOERROR}$, updates transport headers with incrementally recalculated checksums, and appends an answer record populated with the remaining TTL and the resolved 4-byte IPv4 address. Crucially, the Question section is left byte-for-byte intact in packet memory, and the answer record utilizes standard 2-byte DNS name compression ($0xc00c$) pointing directly to the original Question name at offset 12. The program then returns \texttt{XDP\_TX} to retransmit the synthesized response immediately at line rate, completely bypassing host interrupts and PCIe traversal (Figure~\ref{fig:hw_pipeline}).

Conversely, on a cache miss, or when processing incoming authoritative responses ($\text{QR}=1$) from upstream nameservers, the SmartNIC executes strictly zero write operations and immediately yields \texttt{XDP\_PASS} to hand the packet to the host. Because the XDP offload hook operates on the network interface's RX (ingress) path, the hardware cache is never populated from host-to-client TX transmissions. Instead, cache ingestion is governed by the \textit{DNS Listener} eBPF program, attached to the host's native or generic XDP layer. As recursive queries are dispatched upstream, the DNS Listener records active in-flight transactions in an eBPF tracking map (\texttt{recursive\_queries}), tracking the 16-bit transaction ID ($\text{TXID}$), the randomized ephemeral UDP destination port, and the requested domain name ($\text{QNAME}$). When an authoritative response arrives on RX, the DNS Listener validates it against the active in-flight state. Only upon verifying an exact match across all three tuples does it extract the validated record and dispatch an event to the \texttt{hw\_sync\_ringbuf} ring buffer. The user-space ingestion daemon (\texttt{daemon\_ingest.c}) then consumes the event, updates the host DRAM timing wheel, and issues an authorized $\mathcal{O}(1)$ \texttt{bpf\_map\_update\_elem} via PCIe DMA to commit the entry into the SmartNIC. This decoupled architecture ensures that external network packets can never directly mutate the SmartNIC cache, providing robust protocol conformance and end-to-end security whether paired with AtesN-DS or a third-party recursive resolver.

\subsection{Architectural Trade-offs: Hardware Offloading and In-NIC Scope}

When designing high-throughput DNS architectures, user-space bypass frameworks such as DPDK~(\cite{kourtis2015enhancing}) and AF\_XDP sockets~(\cite{10.1145/3281411.3281443}) represent well-known alternatives. However, selecting XDP hardware offloading over these host-side paradigms was guided by three key architectural considerations. First, the primary research objective of this work is to evaluate packet processing executed directly within programmable SmartNIC silicon, which neither DPDK nor AF\_XDP permits. Crucially, no host-side framework can answer a query before it physically crosses the PCIe bus and consumes host memory bandwidth. Second, DPDK relies on aggressive Poll Mode Drivers (PMD) that monopolize 100\% of dedicated CPU cores in busy-waiting loops even under low traffic, contradicting our goal of liberating host resources for recursive resolution. Third, DPDK's complete kernel bypass severs integration with the OS network stack, requiring routing, firewalling (iptables/nftables), and protocol edge cases (such as TCP fallbacks for truncated responses) to be entirely re-implemented in application code. In contrast, eBPF/XDP hardware offloading resolves cache hits in silicon with zero host CPU datapath overhead, while preserving a cooperative model where cache misses, non-A queries, and long-tail packets fall through cleanly via \texttt{XDP\_PASS} to the native Linux network stack and existing resolver software. While running eBPF firmware on the SmartNIC can supersede certain fixed-function ASIC pipelines (such as generic L4 checksumming), absorbing millions of queries in silicon with sub-microsecond latency provides far greater system relief.

A complementary architectural question is \textit{why offload only a caching layer instead of a fully-fledged recursive resolver into hardware?} From a workload perspective, real-world DNS traffic follows a highly skewed, Zipfian distribution heavily concentrated around a small subset of high-frequency domains~\cite{10.1145/505202.505223}. Because the vast majority of incoming queries target these popular records, offloading a lightweight caching layer alone captures nearly all potential query hits where line-rate, sub-microsecond acceleration provides systemic relief to the host. Conversely, attempting to push full recursive resolution into silicon yields diminishing returns. Recursive resolution is an inherently complex, long-running operation involving pending socket tracking, intermediate referral parsing, and timeout retries across authoritative servers. Accelerating these long-tail cache misses in hardware provides negligible performance gains, as their latency is overwhelmingly dominated by wide-area network (WAN) round-trip times (RTTs) rather than host processing overhead.

Furthermore, attempting to implement stateful recursive logic is fundamentally obstructed by the low-level constraints of eBPF/XDP offloading established in Section~\ref{sec:implementation}. As highlighted in prior eBPF offload studies~\cite{tibav:41657} and confirmed by our implementation, SmartNIC execution environments enforce strict silicon and verifier boundaries. The 4,096 assembly-like instruction budget and the lack of program chaining via tail calls (\texttt{bpf\_tail\_call}) prevent decomposing complex recursive state machines into modular BPF programs. Most critically, maintaining active tracking contexts for recursive queries demands at least 256 bytes per record, fundamentally exceeding the entry footprint and memory constraints enforced by SmartNIC eBPF map offloading. 

Consequently, our implementation proves that pairing a high-throughput hardware cache for line-rate hit absorption with host-based software recursive fallback represents the optimal architectural trade-off between hardware performance and software flexibility.

\subsection{Realistic DNS Cases, Cache Poisoning Protection, and Operational Scope}
\label{sec:threat_model}

A critical architectural consideration for in-silicon DNS acceleration is how the system handles diverse protocol semantics, attack vectors, and operational edge cases without sacrificing hardware performance or protocol conformance. To reconcile line-rate acceleration with the vast complexity of RFC standards, our architecture establishes a strict division of responsibility: the SmartNIC data plane is specialized as a line-rate fast-path cache strictly for $\text{QTYPE}=\text{A}$ and $\text{QCLASS}=\text{IN}$ records up to 56 bytes, while all complex, non-A, or long-tail DNS behaviors gracefully cascade to the host driver and user-space resolver stack via non-disruptive \texttt{XDP\_PASS} fallback.

\textbf{Specialization to IPv4 A/IN Records.} Specializing the hardware table exclusively to $\text{A}/\text{IN}$ queries represents a deliberate design decision guided by empirical traffic distributions: IPv4 A-record queries constitute over $85\%$ to $90\%$ of enterprise volume~\cite{SINGH201914}. By evaluating $\text{QTYPE}=1$ and $\text{QCLASS}=1$ inline at the packet parser, the lookup table dispenses with multi-byte type and class fields, dedicating its key budget entirely to the domain name. This enables the compact 64-byte entry layout ($56\,\text{B}\text{ key} + 8\,\text{B}\text{ value}$) matching the hardware's 64-byte alignment boundary and fitting within the 1,536 native NFP instruction limit.

\textbf{Graceful Fallback for Complex DNS Query Types.} Rather than dropping or rejecting unsupported query formats, the offloaded ingress parser inspects the DNS question headers and immediately returns \texttt{XDP\_PASS} with zero packet loss for the following cases:
\begin{itemize}
    \item \textbf{Long Domain Names ($>56$ bytes):} Queries targeting domain names exceeding 56 characters cannot be indexed in the 56-byte hardware table. These queries bypass hardware lookup and cascade untouched to the host driver-space resolver.
    \item \textbf{Alternative Query Types (\texttt{AAAA}, \texttt{CNAME}, \texttt{MX}, \texttt{TXT}, \texttt{SRV}, \texttt{PTR}):} Incoming queries requesting IPv6 addresses (\texttt{AAAA}), alias chains (\texttt{CNAME}), mail routing, or text records immediately pass to host software via \texttt{XDP\_PASS}, where the full recursive resolver resolves intermediate alias chains or upstream authoritative records.
    \item \textbf{DNSSEC Cryptographic Validation ($\text{DO}=1$):} Cryptographic signature verification (\texttt{RRSIG}, \texttt{DNSKEY}, \texttt{DS}) requires complex asymmetric cryptographic primitives, dynamic chain traversal, and large payload handling incompatible with SmartNIC microcode budgets. All queries advertising the DNSSEC OK ($\text{DO}$) flag bypass the hardware cache to be validated securely in host software.
    \item \textbf{EDNS0 and Large Payloads ($>512$ bytes):} Queries advertising large EDNS0 buffer sizes or multi-record RRsets pass to host space, preventing hardware buffer overruns and fragmentation issues.
    \item \textbf{Stateful TCP Fallback:} The SmartNIC offload hook strictly filters stateless UDP frames on port 53. If a response exceeds the maximum transmission unit or triggers a truncation flag ($\text{TC}=1$), the client reissues the query over TCP; all TCP SYN/ACK handshakes pass directly into the native Linux TCP/IP network stack for full connection management and stream reassembly.
    \item \textbf{Negative Caching (\texttt{NXDOMAIN}):} Negative caching requires storing variable-length SOA records and authoritative negative proofs, which would fragment the fixed 64-byte hardware table. Consequently, NXDOMAIN caching is managed entirely within the driver-space resolver cache.
\end{itemize}

\textbf{Cache-Poisoning Protection and Security Model.} Operating an autonomous in-NIC responder introduces two primary security considerations: unauthenticated record injection and DNS reflection attacks. First, to prevent arbitrary wire packets from poisoning the hardware cache, the offloaded SmartNIC program contains strictly zero packet-triggered map-write operations; all incoming responses ($\text{QR}=1$) arriving from external networks immediately yield \texttt{XDP\_PASS} to the host stack. Cache mutation is mediated exclusively through the host-side \textit{DNS Listener}. As recursive queries are dispatched upstream, the DNS Listener statefully records active transactions in an eBPF tracking map, capturing three high-entropy tuples: the randomized 16-bit Transaction ID ($\text{TXID}$), the randomized ephemeral UDP destination port, and the question name ($\text{QNAME}$). Only when an incoming authoritative response strictly matches an outstanding in-flight query across all three tuples does the DNS Listener extract the validated record and dispatch an event to the host ring buffer (\texttt{hw\_sync\_ringbuf}). A privileged host user-space daemon subsequently commits the record to the SmartNIC lookup table via \texttt{bpf\_map\_update\_elem} over PCIe DMA. Because external network packets can never directly mutate hardware memory, cache poisoning via spoofed wire packets is physically impossible. Second, to mitigate DNS reflection and amplification DDoS, the SmartNIC responder exclusively synthesizes single IPv4 \texttt{A} answers mirroring client questions, strictly bounding the response-to-query size ratio to $\approx 1.0\times$ (eliminating volumetric amplification leverage). Queries requesting potentially amplifying types (such as \texttt{ANY}, \texttt{TXT}, or EDNS0 payloads exceeding 512 bytes) bypass hardware via \texttt{XDP\_PASS} to host-level response rate limiting (RRL).

\section{Evaluation}
\label{sec:evaluation}
This evaluation quantifies the performance and efficiency gains achieved by augmenting the eBPF-based DNS resolver with a hardware-accelerated caching layer. To isolate the exact impact of SmartNIC offloading, we compare two operational deployments of the system: a baseline driver-space execution (\texttt{driver-mode}) and the proposed hybrid architecture with hardware offloading (\texttt{offloaded-mode}). Both configurations build upon the AtesN-DS framework~(\cite{sbesc_estendido}).

To ensure exact reproducibility, the AtesN-DS stack was instantiated with identical eBPF map dimensions across both deployments. Specifically, the host-side state plane was provisioned with a ring buffer (\texttt{ringbuf\_send\_packet}) with a capacity of $2^{24}$\,bytes ($16$\,MB) for asynchronous user-space event dispatching. State tracking and caching in driver space relied on an LRU hash map (\texttt{recursive\_queries}) with $65,536$ entries for client query ownerships, a primary pending query tracking map (\texttt{new\_queries}) with $4,587,576$ entries, a primary A-record cache (\texttt{cache\_arecords}) capped at $4,000,000$ entries, and an NS-record cache (\texttt{cache\_nsrecords}) provisioned with $8,000,000$ entries.

Using identical, realistic trace-driven workloads on a physical point-to-point testbed, this study evaluates how introducing the hardware-offloaded data plane improves throughput, latency, and host CPU efficiency compared to purely driver-space processing. For the \texttt{offloaded-mode} experiments, the multi-tier caching pipeline was provisioned with a $2,000,000$-entry \texttt{hw\_cache} map hosted in the SmartNIC's onboard DRAM, reaching the firmware-supported map allocation ceiling for offloaded eBPF hash tables and thereby maximizing the hardware cache capacity, while working in tandem with the driver-space resolution stack to absorb misses.

The experimental testbed was provisioned as a fully isolated, closed-loop point-to-point network completely disconnected from the public Internet. By eliminating any external WAN connectivity, upstream ISP routing jitter, and fluctuating Internet latency, this air-gapped environment guarantees strict determinism, zero packet interference, and exact experimental reproducibility, ensuring that all observed performance metrics reflect solely the raw packet processing capabilities of the SmartNIC hardware and the host resolution stack. Physical interconnection between the two dedicated server nodes is established over a direct 10GbE fiber-optic link. The target resolver server is equipped with an Intel Core i7-8086K CPU (6 cores at 4.00\,GHz), 14\,GiB of RAM, Ubuntu 22.04.5 LTS, and a Netronome Agilio CX 10GbE SmartNIC (serving as the device under test and operating interchangeably in driver-mode and hardware-offload mode). The load-generating client machine features an Intel Core i7-4790 CPU (4 cores at 3.6\,GHz), 10\,GiB of RAM, Ubuntu 24.04 LTS, and an Intel X710 10GbE NIC acting as an unaccelerated external traffic source. Using a commodity Intel NIC on the client isolates load generation from SmartNIC-specific optimizations, faithfully modeling standard network client traffic. Furthermore, to prevent offload asymmetries from confounding measurements, host-level NIC offload features (such as Generic Receive Offload, GRO, and Large Receive Offload, LRO) were kept strictly identical across both driver and offload modes via \texttt{ethtool}.

To evaluate resolver performance under realistic traffic distributions rather than synthetic uniform queries, we deployed the high-performance \texttt{dnspyre}~(\cite{dnspyre}) benchmarking framework driven by a real-world enterprise DNS traffic dataset collected across an active university campus network\footnote{\url{https://www.kaggle.com/datasets/daumel/dns-tunneling-dataset}}. Originally gathered across a 10-day monitoring campaign and established as a benchmark in empirical DNS fingerprinting and anomaly detection studies by~\cite{SINGH201914}, this dataset captures genuine enterprise query patterns, domain popularity skewness, and natural temporal locality. Specifically, our evaluation replays the initial 60-second operational window from the Friday capture session (representing peak weekly campus activity). This trace-driven setup subjects the hybrid resolver to a realistic blend of high-frequency popular domains that can be served directly from the SmartNIC's hardware cache, alongside long-tail recursive requests that fall back to the host data plane. Concurrently, a custom kernel instrumentation daemon recorded host CPU utilization, distinguishing user-space execution, kernel routines, and SoftIRQ overhead. Each benchmark run was preceded by a cache-warming phase and executed for 60 seconds. To guarantee statistical significance, all experimental configurations were repeated 30 times across every concurrency level, reporting mean values and standard deviations across all metrics (with error bars representing 95\% confidence intervals plotted across all figures, which appear visually compact due to tight measurement consistency).

\subsection{Throughput and Speedup Analysis}
The throughput results are shown in Figure~\ref{fig:throughput}. The \texttt{driver-mode} baseline grows from 3,326\,Queries/s (199,556 queries/min) at single-connection baseline and plateaus near 101,800\,Queries/s (6.11\,M queries/min) across 128 to 8,192 concurrent connections, before settling at 99,408\,Queries/s (5.96\,M queries/min) at 16,384 connections. In contrast, the \texttt{offloaded-mode} design scales substantially faster, reaching a peak throughput of \textbf{172,468\,Queries/s} (\textbf{10.35\,M queries/min}) at 128 connections and sustaining over 151,000\,Queries/s (9.08\,M queries/min) across the entire high-load plateau up to 16,384 connections.

This gap comes from the two systems' different hardware-software boundaries. In \texttt{driver-mode}, every DNS query must traverse the NIC RX queues, cross the PCIe bus, and trigger a hardware interrupt. That interrupt makes the host schedule SoftIRQ handlers to run the eBPF parser and lookup logic on a CPU core. As concurrency grows, this software-bound path becomes a bottleneck. Packet descriptors and payloads keep moving across PCIe, and interrupt handling consumes more host cycles.

Conversely, the \texttt{offloaded-mode} architecture bypasses the host's hardware and software stack for cache-hit transactions. By offloading the eBPF data plane directly onto the SmartNIC's programmable Network Processing Units (NPUs) and hosting the lookup tables in high-speed onboard SmartNIC memory, the system intercepts and resolves DNS queries at line rate. Because cache hits are resolved entirely on-NIC, the packets are immediately retransmitted via \texttt{XDP TX} without crossing the PCIe bus, triggering host interrupts, or consuming host CPU cycles. 

This design effectively decouples incoming traffic volume from host operating system performance, yielding a substantial reduction in host SoftIRQ overhead, a phenomenon visible in Figure~\ref{fig:cpu_softirq}. Across the operational saturation plateau (64 to 4,096 connections), the offloaded architecture sustains a consistent \textbf{1.64}$\boldsymbol{\times}$ to \textbf{1.70}$\boldsymbol{\times}$ speedup (+64\% to +70\% gain) over the baseline (shown in Figure~\ref{fig:speedup}), peaking at a maximum relative speedup of \textbf{1.80}$\boldsymbol{\times}$ at 4 concurrent connections (+80.38\% higher throughput, jumping from 22,847 to 41,211\,Queries/s, representing an additional 1.10\,M queries/min), while maintaining a robust \textbf{1.52}$\boldsymbol{\times}$ speedup (+52.32\%) under peak stress of 16,384 connections.

\subsection{Hardware Cache Hit Rate Dynamics}

The performance gains of the hybrid architecture directly stem from the filtering efficiency of the SmartNIC hardware cache layer. Figure~\ref{fig:cache_hit_rate} depicts the hardware cache hit rate across all evaluated concurrency levels. At low concurrency (1 and 2 connections), the hardware cache registers a hit rate of \textbf{59.9\%} and \textbf{59.4\%}. As concurrency ramps up, the hit rate increases to \textbf{62.3\%} (at 4 and 8 connections), \textbf{66.1\%} (at 32 connections), and stabilizes at a steady plateau of \textbf{72.2\% to 72.8\%} across the entire 64 to 16,384 concurrency range (peaking at 72.83\% at 128 connections).

This stable $\sim 72.8\%$ hit rate confirms that nearly three-quarters of all incoming client requests are resolved and transmitted immediately within the network interface silicon. Crucially, analyzing the remaining $\sim 27.2\%$ of queries that trigger driver-space fallback reveals the direct impact of the hardware memory layout. Specifically, the \texttt{hw\_cache} table enforces a 56-byte key boundary (\texttt{char[56]}). Queries targeting domain names exceeding 56 bytes in length cannot be indexed in the hardware table and are therefore transparently forwarded to the driver-space resolution pipeline, alongside cold misses, non-A query types, and expired TTL entries. Despite this structural constraint, the 56-byte hardware cache successfully absorbs the vast majority of real-world traffic, drastically reducing host-level interrupt generation, PCIe bus contention, and operating system overhead.

\subsection{Host CPU Efficiency and Computational Productivity}

The primary objective of hardware offloading is to decouple network packet processing from the host's computing infrastructure, liberating CPU resources for general-purpose applications. This architectural decoupling is evaluated along four dimensions: the host's Software Interrupt (\textit{SoftIRQ}) overhead, the utilization profile of the most strained CPU core, global host CPU utilization, and computational efficiency, as captured in Figures~\ref{fig:cpu_softirq}, \ref{fig:max_core_usage}, \ref{fig:cpu_total}, and~\ref{fig:cpu_efficiency}.

In standard eBPF/XDP driver mode, network processing forces the host OS to allocate substantial cycles to SoftIRQs to receive, parse, and route packets within kernel space. As shown in Figure~\ref{fig:cpu_softirq}, the baseline \texttt{driver-mode} configuration scales its SoftIRQ consumption rapidly, consuming up to \textbf{2.45\%} of global CPU capacity solely on packet reception under 16 concurrent connections and remaining near 2.0\% across the plateau. Conversely, the \texttt{offloaded-mode} configuration mitigates this overhead by resolving hits directly at the silicon layer: by intercepting packets on the SmartNIC and suppressing host-level interrupts, it reduces SoftIRQ overhead by up to \textbf{36.5\%} (dropping to 1.56\% at 16 connections and remaining below 1.42\% across the entire evaluation envelope).

This efficiency gains further granularity when observing the mean utilization of the most heavily loaded CPU core, shown in Figure~\ref{fig:max_core_usage}. In both architectural setups, packet execution bottlenecks tend to concentrate on a single core due to network interface queue bindings and driver interrupt pinning. Under the \texttt{driver-mode} baseline, maximum core utilization climbs to \textbf{10.38\%}. In contrast, the \texttt{offloaded-mode} configuration shields the primary processing core, keeping its average utilization strictly below \textbf{7.85\%} across all evaluated scenarios (averaging 6.8\% across the plateau). By offloading the lookup engine and data plane directly to the SmartNIC, the system not only reduces global system interrupts but also mitigates localized hot-spotting on the network-bound core, confirming that the hybrid architecture decouples high-throughput DNS handling from single-core saturation limits.

Because evictions are performed individually on demand rather than in disruptive bulk bursts, the SmartNIC hash map experiences zero spinlock contention, preserving line-rate resolution with zero forwarding stalls, zero drops, and zero latency jitter even under severe working-set saturation.

\textbf{SmartNIC Silicon Resource Footprint and Interconnect Overhead.} 
In addition to datapath throughput, deploying stateful network functions on programmable network cards is bounded by physical hardware resource constraints. In our architecture, the offloaded pipeline was audited across four hardware dimensions:
\begin{enumerate}
    \item \textbf{Microcode Instruction Budget:} The optimized eBPF bytecode consumes exactly \textbf{589 native instructions}, representing only \textbf{38.3\%} of the Netronome NFP-4000 microengine's strict 1,536-instruction ceiling (\texttt{MAX\_HW\_INSNS = 1536}), preserving over $61.7\%$ of instruction memory headroom for future extensions.
    \item \textbf{Onboard Memory Footprint:} The 2,000,000-entry \texttt{hw\_cache} table occupies exactly \textbf{128\,MB} of onboard SmartNIC DRAM ($64\,\text{B} \times 2{,}000{,}000$). Entries are preallocated in silicon with zero memory leaks, deterministic slot reuse, and zero dynamic memory fragmentation.
    \item \textbf{PCIe Bus Bandwidth:} Background clock synchronization generates a negligible \textbf{24\,B/s} ($<0.001\%$ of bus bandwidth), while maximum demand replacement under working-set saturation bursts consumes $515.0 \pm 18.1\,\text{MB/s}$ (\textbf{12.9\%} of the available 4,000\,MB/s bandwidth on PCIe Gen3 $\times8$), leaving over $87.1\%$ of the bus completely free for packet DMA.
    \item \textbf{Host Interrupt Suppression:} By resolving up to $72.8\%$ of all queries directly in silicon, the SmartNIC suppresses host packet DMA completions and PCIe interrupt generation, cutting host SoftIRQ utilization by up to \textbf{36.5\%} and shielding host CPU cores from interrupt livelock.
\end{enumerate}

\section{Conclusion and Future Work}
\label{sec:conclusion}

This paper presented a hybrid, multi-tier DNS resolver architecture that extends the AtesN-DS framework by integrating an eBPF/XDP driver-space recursive engine with an XDP hardware-offloaded caching layer running directly inside a programmable SmartNIC. The primary objective was to offload key DNS resolution tasks onto dedicated silicon, simultaneously maximizing packet processing performance and alleviating resource pressure on the host infrastructure. By resolving cache hits directly on the SmartNIC data plane, the proposed design effectively isolates the host operating system from query processing overhead for the vast majority of incoming traffic.

Evaluating whether offloading the resolver's caching layer to hardware is worth the engineering complexity yields a clear, affirmative conclusion. Implementing this architecture demonstrates that the primary bottleneck in stateful SmartNIC offloading is not the physical silicon capability, but rather adapting application semantics to fit the constrained eBPF offload runtime environment. Although overcoming limitations, such as the unavailability of time-based eBPF helpers (e.g., \texttt{bpf\_ktime\_get\_ns()}) and the absence of native LRU map support (\texttt{BPF\_MAP\_TYPE\_LRU\_HASH}), requires hybrid design patterns like periodic host clock synchronization and user-space housekeeping daemons, these architectural trade-offs prove remarkably efficient. The main takeaway is that offloading does not need to handle 100\% of complex application logic in hardware to be effective; even a constrained, application-agnostic hardware cache operating transparently in front of the resolution engine provides substantial system relief. By filtering high-frequency hits at line rate, the host operating system is shielded from CPU interrupt storms and PCIe bus traversals, transforming the traditional network stack into a highly deterministic processing engine.

These architectural dividends were empirically validated on a physical point-to-point testbed driven by a real-world campus network trace, where experimental evaluations confirmed the substantial performance and resource efficiency gains of this hardware-decoupled design. Across the operational saturation plateau (64 to 4,096 concurrent connections), the hardware-accelerated caching layer sustained a consistent \textbf{1.64}$\boldsymbol{\times}$ to \textbf{1.70}$\boldsymbol{\times}$ speedup (+64\% to +70\% throughput gain), peaking at a maximum relative speedup of \textbf{1.80}$\boldsymbol{\times}$ at 4 concurrent connections (+80.38\% gain) compared to the standard driver-mode baseline, reaching a peak overall capacity of \textbf{172,468\,Queries/s} (\textbf{10.35\,M queries/min}) and sustaining a robust \textbf{1.52}$\boldsymbol{\times}$ speedup at 16,384 concurrent connections. In terms of response latency, the proposed architecture reduced mean response times by up to \textbf{38.10\%} for workloads up to 4,096 connections, keeping average latency strictly in the sub-millisecond range across the operational plateau while expanding the throughput-latency saturation knee beyond 166,000\,Queries/s. The SmartNIC hardware cache attained a stable hit rate of \textbf{72.2\% to 72.8\%}, resolving over 7.5 million requests directly in silicon and transparently delegating only long-tail requests (such as queries exceeding the 56-byte hardware key limit) and cold misses to the driver fallback. From an infrastructural perspective, shifting query handling to hardware reduced host SoftIRQ utilization by up to \textbf{36.5\%}, boosted computational efficiency by \textbf{+120\% to +141.6\%} (consistently sustaining over \textbf{91,000\,Queries/s per 1\% host CPU}), and kept global server CPU consumption strictly below \textbf{2.15\%} (representing a \textbf{25\% to 33.6\%} reduction in total host CPU demand across the saturation plateau), while capping the utilization of the most strained network core below \textbf{7.85\%}.

For future work, we plan to investigate dynamic, low-overhead cache state synchronization algorithms to further alleviate control plane overhead during high-frequency update bursts. Additionally, we intend to explore automated multi-block parsing optimizations to support complex DNS query types, such as stateful TCP fallbacks and DNSSEC validation, directly within the constrained hardware limits of programmable SmartNICs without triggering host fallback paths.
